# §1 Publication Format Design

> Note: paths are reproduced as-is; Chinese directory names are literal.

## What this section answers: where this piece gets published and what it looks like — the "publication format TBD" left over from v1 is settled here.

Conclusion first: **a single GitHub repository**, with the README as the entry point, the body split into per-chapter files under `docs/`, and image assets under `assets/`. Every rationale and accompanying rule comes from the same-day, actually-read format research (`tasks/t-20261122-archive-v2/github-format-research.md`, cited below as fmt, marked section by section).

**Why not one long article crammed into the README**: the content volume (twelve body chapters plus appendices) exceeds a reasonable README reading length; GitHub's own guidance says the README should cover "what it is / how to use it / how to participate," with long content split into docs/ and linked from the README (fmt §1). GitHub auto-generates an Outline for any file with multiple headings, so splitting into chapters loses no navigation (fmt §2).

**Dual-track rendering**: the goal is readability on both GitHub and Zhihu. Every GitHub-only extension syntax in play — callouts (`> [!NOTE]`), `<details>` folding, footnote syntax, Mermaid diagrams, task lists (fmt §3) — ships with a Zhihu fallback: callouts degrade to blockquotes, folded content moves into an appendix file, footnotes become inline expansions in the "Appendix E glossary" lines, every Mermaid diagram gets a mandatory text equivalent, and task lists degrade to plain lists. The body is drafted once and works on both tracks (fmt §4).

**Figures**: four Mermaid diagrams in the article (role topology / dispatch chain / watchdog evolution chain / the three close-out shapes), each followed by a fixed "text equivalent" paragraph — GitHub renders the diagram, Zhihu gets the text version, and both carry the same information (fmt §4).

**Code blocks**: always carry a language identifier (`python`/`bash`/`diff`); block contents pass the same redaction standard; but **raw error output is a forensic asset and is not redacted** — the paths and usernames inside error stacks are part of the "six tool-error families" evidence chain, and redacting them would destroy verifiability (fmt §5, paired with the six-family files in `docs/09-踩坑.md`).

**If issues are opened**: following the upstream research conclusions — English, reproducible steps, paths and dates attached (fmt §7, `survey-queue-upstream-github-20261120.md`, sections 5-7). This is the same discipline as this article's "every number is checkable against the disk."

**G1's three items are ruled** (Owner, 2026-11-22 14:56): the repository name is not hard-coded in the text — the published draft uses a placeholder name, and the actual GitHub name is set by the Owner at publication time; the license is **MIT** (aligned with upstream; LICENSE ships with the published draft; fmt §6 verified upstream's current license value and set the convention of re-fetching it on the citation date); the README byline follows the author's own convention, with no agent names — the same baseline as verification item ① "JC = the author himself." G3 was ruled the same day: security-sensitive script files do not ship with the repository; the README notes that they "exist but are not public."
