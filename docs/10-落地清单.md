# §10 The Landing Checklist

What this section answers: what the reader does first, and why the order cannot be reversed. The ten-step list is kept as-is (master-structure doc §7), each step gaining one verification action — the checklist itself is the L1 use-case set: walking the checklist is running one full pass of the whole chain.

> Note: paths are reproduced as-is; Chinese directory names are literal.

1. Create the group and directories (2775/664). Verify: `stat -c '%a %G'` on any new directory = 2775 with group inheritance; new files 664. Do not skip the setgid check — the drift incident in §5⑤ was seeded right here.
2. Write README.md (file naming and review norms). Verify: a newcomer, following the README alone, can create a valid task-id directory unaided.
3. Define the roles (pm / wh / plan-jc; the ops lane: discussion / main / om-jc; the minimum can be cut to three functions: dispatch / execute / review). Verify: in each role's AGENTS.md the "must not do" column is non-empty — an empty prohibition list equals no role at all.
4. Write AGENTS.md (duties plus prohibitions). Verify: pick any prohibition at random and ask "if this is violated, where does the disk show it?" If there is no answer, it was never written into the machinery.
5. Build the task bus (tasks/reviews/outputs). Verify: hand-build a dummy task running the SPEC/status two-file flow; status.json contains one of the five legitimate states in §8.
6. Run one minimal L1 item (within 5 minutes). Verify: this step has a measured template — the minirerun-01 regression item went dispatch→done in 5 minutes (21:20 dispatched, 21:28 code delivered, 21:34 closed, A1-A5 all green; the recipe is in staging-v1-drafts/07-02). If 5 minutes is not enough, the bus or a role card has a defect — fix it before putting a real project on it.

> The minimum runnable instance for this step (wordcount, 9 tests all green) is in attachment [A-minirerun](../attachments/minirerun-minimal-instance.md).
7. Test one reject loop once (write it wrong on purpose; see whether it gets stopped). Verify: fixture tasks book task-local per §9.2.1, and the global reject_count stays untouched (recompute with the mtime forensic method).
8. Test one timeout (see whether the dog barks). Verify: dog-watch.log gains a "bark#" line and the corresponding agent gets nudged; in the ledger, pre-written initialization events do not bark — only a recurrence inside the recurrence window escalates. If the dog does not bark, fix the dog first — steps 7-9 on the real ops lane are simply §6 in full: gate before vehicle; the dog itself must also have a baseline, a review, and a rollback.
9. Test one rebuild (can it pick up after a container restart). Verify: after restart, the SPEC/context/status trio of any in-flight task is readable and its state resumable. If it cannot resume, you stored state inside the session (§5①).
10. Only then bring in a real project.

The reason the order cannot be reversed fits in one sentence: **gate first, then vehicle.** Steps 7-9 are "testing the gate" — rejects get stopped, timeouts bark loudly, restarts reconnect. Going live before these three are verified is driving a car with untested brakes on the road. This cluster's own order is the cautionary counterexample: the real project ran first and the gates were retrofitted mid-run; within two weeks the watchdog standard changed three generations and the count authority was fought over twice — every remedial bill cost more than installing the gate up front.

The checklist's second value: ten steps are ten regression cases. After any system upgrade (new model, new permission baseline, new role), rerun from step 6 to step 9 — half an hour to confirm nothing regressed. Late on, this cluster did exactly that after every ops-item merge.

How to verify: this section introduces no new numbers; every verification action above can be executed on the spot on an installed system's disk.
