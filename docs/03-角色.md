# §3 Role Design

> Note: paths are reproduced as-is; Chinese directory names are literal.

What this section answers: six roles split across two loops, what each one "does," and — more importantly — what it "must never do."

First the origin of the word, because it explains why the whole table looks the way it does. JC was not designed; it grew. In the 2026-09-04 article, JC was the author himself (/shared/projects/_writing/materials/素材/文章-AI不负责.md — that original is the "birth certificate" of this mechanism); three months later it split off dedicated review seats from the starting point of "I review everything myself"; after the 2026-11-22 baseline unification, review examines plans and code as one unit, with one seat per loop (business line plan-jc, ops line om-jc). The role history makes one point — this table was not drawn as an architecture diagram; it was forced to split, under review volume, out of the starting point of "I review everything myself." When single-point review can no longer hold, the seats appear on their own.

The second "growing" happened on 2026-11-21: on Owner instruction, a new local agent, discussion, was created — permissions limited to reading and writing its own workspace plus network access; exec/process/browser and the rest all denied — and main was converted into a pure executor; the collaboration flow was finalized the same day: Owner and discussion settle things, then write them to disk; main produces the plan; om-jc reviews it until unconditional pass; discussion instructs main to execute (source: /shared/projects/_ops/discussion-handoff/materials/_supplement-discussion-summary-20261121.md §1.1-3, cited below as sup). This table proves the point a second time: roles grow, they are not designed — but both times the growing stayed inside the existing iron rules, and the first line of discussion's permission list is "it cannot exec."

The two-loop six-role table (6 roles = 2 loops × 3 functions: dispatch / execute / review; the full version is in /shared/projects/_writing/materials/技术总结/大结构.md §2; only how to read it is given here):

| Loop | Role | Function | Must never do |
|---|---|---|---|
| Ops loop (host) | discussion | discuss and dispatch (the PM of the business loop) | cannot exec (nailed down on day one) |
| Ops loop (host) | main | execution + the ops/debug/fix lane (the WH of the business loop) | never ghostwrite signed content |
| Ops loop (host) | om-jc | reviews plans and code as one unit | never writes code, never changes code |
| Business loop (WSL) | pm | clarify, grade, dispatch, verify form, close out | never writes code, never does technical review |
| Business loop (WSL) | wh | writes and changes code strictly on instruction | makes no architecture decisions, no final judgment |
| Business loop (WSL) | plan-jc | reviews plans and code as one unit | never writes code, never changes code |

The two loops are isomorphic: each function has one seat in each loop, differing only in runtime environment (host / WSL). Reading this table takes one rule of thumb: **the "must never do" column matters more than the "does" column.** The does column is the division of labor; the must-never-do column is the defense line. Get the division of labor wrong and efficiency suffers; break the defense line and the books go false.

Three counterintuitive points in the table are the easiest to miss when copying this setup.

First, review is not split by "plan/code"; a reviewer examines plans and code as one unit. The split happens along the loop dimension — business line plan-jc, ops line om-jc, each reviewing the plans and code inside its own loop. om-jc was built on 2026-11-17 14:55 by cloning jc and adding network access, and the root cause of its capability difference from jc turned out to be a missing ca-certificates package in the container (materials pack §2) — one certificate package decided which review seat could go online to verify. Details like this must be written into the role card: instance-level environment differences directly rewrite a role's capability boundary; if the card does not say it, the first time it triggers it shows up as a "fault."

Second, every seat gets its red lines drawn before its authorizations. PM holds sole write rights over reject_count (other sessions read-only, §7 counting case), and the price is that PM itself cannot write code — the urge to code is PM's most common overreach; main holds full ops authority (including the debug/fix lane) but alone may not ghostwrite signed content (§5⑥ anti-ghostwriting red line); an executor, once it hands something over, must shut up — the word "fine" does not exist for it (iron rule three, §4). Reverse the order — grant authority first, add prohibitions later — and the seat is bound to overreach, and overreach throws no error; it only makes the books stop balancing afterward.

Third, PM's "close-out" is not adjudication. When PM marks closed, the action is formal verification: check that the review record is on disk, fields complete, counts aligned — then write it down. The quality judgment happens in the jc channel (§7); PM merely writes an already-established result into the state machine. Understand this and you understand why, among the state machine's five states, an executor can never reach pass — pass is a product of the review channel, never an executor's self-declaration.

The 09-04 line "AI is not responsible for generating the plan" is the birth certificate of the whole structure: plan responsibility sits with the human; AI carries execution and the formal side of review. Three months later that sentence was unpacked into §4's three iron rules, but the role table is its first landed form — first nail down "who may not touch what," and responsibility gets somewhere to hang.

How to verify: each of the six roles has a workspace and an AGENTS.md responsibility card; cross-role rules are in /shared/docs/AGENTS-common.md; the two end-point proofs of JC's semantic evolution are the 09-04 original and the three jc session directories. Spot-check method: pick any role card and check that every entry in its "must never do" column is backed by a mechanism (a state-machine field, a sole-write right, or the context signature rule).


## Figure: role topology (rendered version)

```mermaid
graph TD
  O[Owner: bystander, upstream of the decision chain, outside the loops]
  subgraph Ops loop (host)
    D[discussion: discuss and dispatch] -->|instruct| M[main: execute + ops lane]
    OJ[om-jc: plans and code reviewed as one] -->|verdict| D
  end
  subgraph Business loop (WSL)
    P[pm: dispatch/count] --> W[wh: execute]
    J[plan-jc: plans and code reviewed as one] -->|verdict| P
  end
  O -.->|settle / final ruling| D
  W -->|the trio to disk| F[(file bus)]
  M -->|the trio to disk| F
  F --> J
  F --> OJ
```

Text equivalent (Zhihu track): the Owner is a bystander — upstream of the decision chain, giving instructions and final rulings, but not a node inside either loop. The two loops are isomorphic: in the ops loop, discussion discusses and dispatches, main executes, om-jc reviews as one unit; in the business loop, pm dispatches, wh executes, plan-jc reviews as one unit. Executors write the trio only to the file bus; reviewers read artifacts from the bus and return verdicts to the dispatch seat — every arrow is one-way, there is no direct edge between reviewer and executor, and information can only flow through files.

Scope note: debugger is not listed separately — it is a responsibility of main's ops lane inside the ops loop (debugging / fix lane / cross-sandbox legwork); after the 2026-11-22 Owner baseline unification it was folded into the main row.
